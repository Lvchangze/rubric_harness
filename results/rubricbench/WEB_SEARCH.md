# 第八个候选：给生成器联网查证的能力（`framed_web`）

> **结论：没有帮助。** dev 600 题上 0.6317 vs `framed` 0.6500，**Δ = −0.0183，p=0.334**，
> 低于本样本量的最小可检出差 0.0383。换「不含 SAFETY」（−0.0179, p=0.368）和
> 「位置受控」（−0.0200, p=0.276）两种口径，结论不变。**没有任何一个域达到显著。**
> holdout 保持 **0/3 未动用**——没有候选过线，花掉一次只能确认「没变化」。

## 1. 为什么值得试这一次

`REPORT.md` §11.2 定的规矩是：不要再写第八个 rubric 候选，**除非它带来一个新的信息源**，
并列出仅有的三类。这一次属于其中的 (b)「能解题」：§9.8 测出专家 rubric 里
**出现在判据中、但不出现在指令中的数字**，落在人类偏好那一侧的概率比随机高
**12.4 个百分点**——那是「知道正确答案」，不是通用的任务理解。
此前十个候选没有一个能查任何东西。

所以这不是又一次改 prompt 措辞，前面七个候选失败的原因（形式、判别性意图、
restraint 平衡、目标分布）都不适用于它。

## 2. 单变量设计

| | `framed` | `framed_web` |
|---|---|---|
| rubric 契约 | `FRAMED_SYSTEM` | **同一份，字节相同**（调用时 assert） |
| 工具 | 无 | `web_search`（DuckDuckGo）+ `wikipedia_lookup` |
| 生成方式 | 单次调用 | 工具循环，最多 4 轮，轮次耗尽时撤掉工具要求交付 |
| judge | `default` profile，冻结 | 同 |

只暴露两个网络工具。把 `agentic-tools` 那另外六个也放进来会混淆归因——这一臂存在的
目的是**单独给「联网查证」定价**，而其余六个已经量过并且输了。

## 3. 结果

dev 600 题，配对 McNemar，参照 `framed`：

| source | forward | 不含 SAFETY | 位置受控 | 相对 `framed` | p |
|---|--:|--:|--:|--:|--:|
| `none`（地板） | 0.5817 | 0.6057 | 0.4867 | −0.0683 | 0.00043 |
| `baseline` | 0.6083 | 0.6308 | 0.5383 | −0.0417 | 0.0223 |
| **`framed`** | **0.6500** | 0.6487 | 0.5700 | — | — |
| **`framed_web`** | **0.6317** | 0.6308 | 0.5500 | **−0.0183** | **0.334** |
| `expert`（天花板） | 0.8083 | 0.8100 | 0.7250 | +0.1603 | 6.4e-19 |

分域，全部不显著：

| 域 | n | `framed` | `framed_web` | Δ | p |
|---|--:|--:|--:|--:|--:|
| CHAT | 220 | 0.6227 | 0.6227 | +0.0000 | 1.00 |
| CODE | 142 | 0.5845 | 0.6127 | **+0.0282** | 0.608 |
| IF | 65 | 0.7077 | 0.6154 | −0.0923 | 0.0703 |
| SAFETY | 42 | 0.6667 | 0.6429 | −0.0238 | 1.00 |
| STEM | 131 | 0.7328 | 0.6718 | −0.0611 | 0.134 |

**唯一为正的是 CODE**（查 API 签名、库行为最可能真的有用），而我事前最看好的 **STEM 反而掉了 6 个点**。
两者都远不显著，n=142 / 131 的域内检出下限比这些 Δ 大得多，所以这个形态**不能当结论**，
只能记为一个待验证的猜想。

## 4. 运行事实

| | |
|---|---|
| 搜索调用 | **1707 次**，覆盖 **431/600 题（71.8%）** |
| 产出非空 rubric | 593/600（7 题未能产出可解析 JSON） |
| 平均判据条数 | 5.15 → **5.75**（搜索让清单变长了一点） |
| 两臂 rubric 完全相同的题 | **0**（确认生成是独立重跑，不是缓存复用） |
| 总耗时 | 1801 秒（生成 ~650s，判定 ~1150s） |

**它在不该搜的地方也搜了。** prompt 明确写了「风格、偏好、安全、任务框定类的指令不要查，
查了也没用还浪费一轮」，但仍有 71.8% 的题触发了搜索——包括「给学生写 90–100 字评语」
这类查无可查的题。搜索占掉的判据位没有换来判别力，这与条数从 5.15 涨到 5.75 一致。

## 5. 这告诉了我们什么

把它和 `ERROR_DECOMP.md` 放在一起读，形态是一致的：

- 错误分解显示 `framed` 的失败里 **72.2% 是判据指错了方向**，只有 3.3% 出在聚合。
- `expert` 的「判据票决准确」是 **0.903**，十个生成候选挤在 **0.588–0.673**。
- 联网补的是「**知道正确答案**」。但失败模式是「**判据没指对方向**」——
  这两者不是一回事。知道 CO₂ 激光是 10.6 μm，并不能告诉你这道题的两个回答
  之间真正的分野在哪里。

所以这次的 null 并不意外，它反而是对 §9.8 那条推断的一个**限定**：
数字 tilt 确实指向「专家知道答案」，但把「知道答案」单独补给生成器，
在本基准上买不到分数。§9.8 那 12.4 个百分点的 tilt 最终只值 0.5–1.5 个准确率点（§9.5），
和这里的 −0.0183 在同一量级上无法区分。

**仍然没有被试过的信息源**只剩 §11.2 的 (a)「允许看两个回答」——
而那已经不是「从指令生成 rubric」这个任务了。
